# UI 信息架构整合方案

> **状态**：PROPOSED
> **提出**：2026-09-02
> **触发**：Boss 反馈「菜单经过几版整合有些乱，含义不清、作用不大」，
> 举任务中心右侧面板为例（任务证据 / 导出 / 建议性审批 / approved / 证据 / 轨迹 / 健康 / 调试）。
> **范围**：`trustos/frontend/src`

---

## 1. 背景

Boss 的原话是「这些按钮作为用户不知所云」。

这不是审美问题，而是**信息架构（IA）问题**：每个迭代往上加功能，
但没有人从「用户要完成什么」的视角回看整体。结果是一个能跑、
但说不清自己是什么的界面。

---

## 2. 现状盘点（事实）

### 2.1 入口总览

主导航 8 项（`app/page.tsx:51`）：

| id | 显示文案 | 渲染组件 |
|---|---|---|
| `chat` | 💬 Chat | `ChatInterface` |
| `tasks` | 📋 Tasks | `views/TasksView` |
| `memory` | 🧠 Memory | `memory/MemoryGovernanceSurface` |
| `archive` | 📦 Archive | `views/ArchiveView` |
| `manager` | 🤖 Manager | `views/ManagerView` |
| `permissions` | 🔐 Perms | `views/PermissionsView` |
| `dashboard` | 📊 Dashboard | `views/DashboardView` |
| `audit` | 🛡️ Audit | `audit/AuditReviewSurface` |

工作台 4 个 tab（`app/page.tsx:53`）：🔍 证据 / ⚡ 轨迹 / 💚 健康 / 🔧 调试。

**合计 12 个顶层入口。**

### 2.2 最大问题：同一个「证据」概念有 3 个 UI、2 套数据源

| # | UI | 位置 | 数据源 |
|---|---|---|---|
| 1 | `TaskEvidenceView` | 工作台顶部（选中任务后） | Gateway 事件（含审批表单、导出） |
| 2 | `EvidencePanel` | 工作台「🔍 证据」tab | `fetchEvidence(taskId)` |
| 3 | `TasksView` 的「🔍 关联证据」 | 任务详情 Block 4 | `EvidenceList` |

三者会**同时出现在同一屏**，内容还不完全一致。用户看到三个「证据」
却不知道该看哪个——这是「菜单混乱」感知的最大来源。

同类重复还有：任务列表出现 2 次（主区 + 工作台顶），轨迹出现 2 次
（主区 + 工作台 tab）。

### 2.3 存在「假功能」——这是信任问题，不只是整洁问题

| 功能 | 实际情况 |
|---|---|
| `TaskEvidenceView` 的审批表单 | `handleApprove()` **不发任何后端请求**（代码注释明写 `No backend call`）。只在浏览器本地算一条 hash 记录，触发一次 `.jsonl` 文件下载。服务端无记录，刷新即失。 |
| 「建议性审批（不阻塞）」 | 同上。用户以为在提交审批，实际只是下载了本地文件。 |
| `AuditReviewSurface` 的「🧪 状态示例」 | 4 张硬编码假卡片，页面上明写「非真实记录」「仅用于演示」，但与真实审核队列混在同一页。 |
| 「导出」按钮 | 导出的是**前端已加载的数据**，不是服务端权威副本。 |

这些不是「做得不好」的功能，而是**演示物被当成产品**。
对普通用户是困惑，对信任型产品是硬伤——本产品卖点恰恰是可追溯与诚实。

### 2.4 开发者视角混入用户视角

- `debug` tab：路由决策、provider/model、latency 明细
- `health` tab：系统 uptime/组件状态（且是**全局**的，与其余任务级 tab 层级不符）
- 任务证据标题栏直接显示**完整裸 UUID**（`TaskEvidenceView.tsx:213`）
- 工作台顶部 220px 的 `TaskPanel` 视觉上与 4 个 tab 连在一起，用户会以为是第 5 个面板

### 2.5 语言与一致性

- 侧边栏全英文（Chat/Tasks/Perms/…），工作台全中文（证据/轨迹/…），
  同一屏中英混排
- `Perms` 是缩写，其余是完整词
- `memory` 视图的显示名是「Memory」，组件叫 `MemoryGovernanceSurface`
- `MemoryGovernanceSurface` 副标题仍是英文「MWT-6 — Inspect memory scope…」

### 2.6 仓库里有 3 份 frontend

- `trustos/frontend/src` ← **当前真实前端**
- `frontend/src` ← 旧副本（无 audit、无 memory governance、用旧 `views/MemoryView.tsx`）
- `20260407104107/smartrouter-pro/frontend/src` ← 更旧副本

后两份已分叉，是误改风险源。

## 3. 问题诊断

不是「菜单太多」这么简单。三个结构性问题：

**① 一个概念，多个入口**
证据 ×3、任务列表 ×2、轨迹 ×2。用户无法建立「这个概念在哪看」的稳定心智模型。

**② 开发者视角与用户视角混编**
系统内部概念（UUID、debug、health、provider latency）直接暴露给用户。
这些对构建者有意义，对使用者是噪音。

**③ 演示物伪装成真实功能**
审批表单不写后端、Audit 有假卡片。用户会基于错误预期行动
（以为审批已记录、以为审核队列里有那几条）。

**根因**：功能按 sprint 累加，IA 从未被当作需要维护的对象。

---

## 4. 设计原则

1. **用户语言**：不出现 UUID、provider、latency、debug 等内部术语。
   必要时提供「复制 ID」而非直接展示。
2. **单一真相源**：同一概念只有一个入口、一套数据源。
3. **任务为中心**：所有功能围绕「我让它做的事」组织，而非「系统里有什么表」。
4. **渐进披露**：高级/运维能力收纳，不铺在表面。
5. **诚实**：假功能要么做真（接后端），要么下线。不做「看起来能用」的演示。
6. **语言统一**：全局中文，内部代号不出现在 UI。

---

## 5. 整合方案

### 5.1 主导航：8 → 5

| 保留 | 显示名 | 说明 |
|---|---|---|
| ✅ | 💬 **对话** | 主工作区 |
| ✅ | 📋 **任务** | 整合证据、轨迹 |
| ✅ | 🧠 **记忆** | 已改好的审核界面 |
| ✅ | 📦 **归档** | |
| ✅ | 🛡️ **审计** | 保留，但**清理假卡片** |

| 处理 | 项目 | 理由 |
|---|---|---|
| 🔀 并入「任务」 | `dashboard` | 其统计信息可在任务页顶部呈现；其 4 处跳转权限的按钮本就与权限视图重复 |
| 🔀 并入「审计」 | `manager` | 两者都是治理/管控视角，用户无法区分；Manager 的内容（决策记录）本就属审计范畴 |
| 🔽 移入设置 | `health` | 运维视图，非日常使用 |
| ❌ 下线 | `debug` | 纯开发者信息；改为环境变量开关，默认关闭 |
| 💡 改名 | `Perms` → **权限** | 去掉缩写 |

> `permissions` 保留在主导航：它有「待处理数量」角标，是需要用户
> **采取行动**的入口，与「查看类」入口性质不同。

### 5.2 工作台：4 → 2

| tab | 处理 |
|---|---|
| 🔍 **证据** | **保留，并成为唯一证据入口**（合并另外两处） |
| ⚡ **轨迹** | 保留 |
| 💚 健康 | 移入设置 → 「系统状态」 |
| 🔧 调试 | 下线（默认关闭，环境变量开启） |

工作台顶部 220px 的 `TaskPanel` 与 4 个 tab 视觉相连的问题：
加明确分隔与标题「任务详情」，消除「第 5 个面板」的错觉。

### 5.3 任务中心：消除重复

当前任务详情页有 4 个 Block（头部 / 摘要 / 执行轨迹 / 关联证据）。
与工作台的证据、轨迹重复。

**方案**：任务详情页作为**唯一真相源**，工作台不再重复。

- 任务详情页保留：摘要、轨迹、证据（完整）
- 工作台的「证据 / 轨迹」tab 改为**仅在工作台独立使用时**显示，
  或彻底移除，把空间还给任务详情

> 倾向后者：工作台与任务详情二选一。既然任务详情页已完整，
> 工作台 tab 整体下线，只保留任务面板。这样「证据」概念全站只有一个入口。

### 5.4 假功能处理

| 功能 | 处理 | 理由 |
|---|---|---|
| TaskEvidenceView 审批表单 | **下线** | 不写后端、只下载文件的「假审批」会误导用户，与产品的可信定位冲突 |
| Audit「🧪 状态示例」卡片 | **下线** | 硬编码 fixture，明写「非真实记录」 |
| 导出按钮 | **保留并修正预期** | 改为「导出当前视图数据」，提示这是前端已加载内容的快照 |

> 若未来需要真实审批，应新建「审批」领域：后端持久化 + 真实审批人身份 +
> 待处理队列。这不是 UI 整合能解决的，应单独立项。

### 5.5 语言与文案

- 侧边栏改中文：对话 / 任务 / 记忆 / 归档 / 审计 / 权限 / 设置
- `Perms` → 权限
- Memory 视图标题与副标题改中文
- 任务证据标题栏：完整 UUID → 显示 `#前8位`，提供「复制完整 ID」按钮
- 审批相关英文（`approved`/`rejected`/`noted`）下线后不再需要翻译

### 5.6 清理废弃副本

`frontend/` 与 `20260407104107/smartrouter-pro/frontend/` 两份旧前端
已分叉，建议删除或移出工作区，避免误改。

> ⚠️ 删除是不可逆操作，需要 Boss 确认。

## 6. 取舍

| | 做 | 不做 |
|---|---|---|
| **认知负担** | 12 → 6 个顶层入口，单一真相源 | 维持现状 |
| **可信度** | 移除假功能，言行一致 | 保留演示物，用户可能基于错误预期行动 |
| **开发效率** | 失去 debug 面板的即时可见性 | 保留（对日常开发确实方便） |
| **成本** | 需重构导航、合并 3 个证据入口、回归测试 | 零成本 |
| **风险** | 删除功能若日后需要，需从 git 历史找回 | 无 |

关于 **debug 面板的取舍**：它对开发确实有用。折中方案是
**默认关闭、环境变量 `TRUSTOS_UI_DEBUG=1` 开启**，而不是彻底删除代码。
这样既清理了默认界面，又保留了排障能力。

关于 **dashboard 的取舍**：它提供了全局统计视角。若 Boss 认为有价值，
可保留为「任务」页顶部的统计条，而非独立导航项。
