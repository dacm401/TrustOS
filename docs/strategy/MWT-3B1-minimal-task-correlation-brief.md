## 1. Summary

This is the **smallest implementable unit** of MWT-3B: add a single nullable `task_id` field to the event envelope and event index. No `run_id`, no `trace_id`, no Evidence report changes, no task auto-creation.

**Design Principle**: Option C (PM preferred) — task_id only, nullable by design.

---

## 2. Why This Scope

| What | Why |
|------|-----|
| Only `task_id` | Minimal conceptual expansion. Already in `task_archives` semantics. |
| Nullable | Pre-task events naturally have no task. Old events won't break. |
| No `run_id` | Requires formal Manager Run model (not yet designed) |
| No `trace_id` | Trust Layer semantics (not yet designed) |
| No Evidence changes | MWT-4 is a separate phase |
| No task auto-creation | Gateway observes, doesn't create |

### 3.3 Wire Format Contract (PM Revision 1)

Inheriting MWT-2 F2 retro: all Gateway/SSE wire payloads MUST use `snake_case`.

```text
Wire field: task_id: string | null

Forbidden on wire:
  ❌ taskId
  ❌ taskID
  ❌ TaskId
```

Frontend may use `camelCase` internally, but MUST map at the parse boundary:

```text
wire task_id → TS taskId  (at API response parse layer)
```

This applies to:
- SSE event payloads (`data: {"task_id": ...}`)
- JSON API responses (`GET /v1/events`)
- Event envelope serialization to JSONL

---

### 3.4 task_id Nullable Semantics (PM Revision 2)

```text
For events ingested after MWT-3B1 deployment:
  task_id MUST be explicit string | null — ALWAYS present on the event envelope.

Allowed:
  ✅ { "task_id": "task_abc" }       — assigned to a task
  ✅ { "task_id": null }              — explicitly unassigned

Forbidden:
  ❌ task_id omitted for new 3B1 event envelope
  ❌ task_id = "" (empty string)
  ❌ task_id auto-generated by Gateway
  ❌ task_id = "unknown" or sentinel values

Historical events (pre-3B1):
  May lack task_id field entirely.
  MUST be treated as unassigned/null at query boundary.
  No forced backfill in 3B1.
  Query layer MUST coalesce (missing task_id) → NULL for filter purposes.
```

---

### 3.5 Ingestion Source (PM Revision 3)

`task_id` MUST come from a trusted context. Gateway MUST NOT fabricate it.

```text
task_id MAY come from:
  1. X-TrustOS-Task-Id header — from trusted Manager/client context
  2. Existing internal request context if already present (e.g., Manager-injected metadata)

task_id MUST NOT come from:
  1. Gateway auto-generation
  2. Parsing user prompt text
  3. Model output inspection
  4. Inferred session title or content
  5. Random/default UUID generation
```

Smoke note: if no trusted header/context exists at test time, the assigned-case smoke MAY use a controlled test client header (`X-TrustOS-Task-Id: task-smoke-001`). This is test-only, not product behavior.

### 3.6 API Surface (PM Revision 4)

Minimal addition — one query parameter on existing `/v1/events`:

```text
PM PREFERRED:
  GET /v1/events?task_id=<id>     — filter events by task_id
  GET /v1/events?task_id=null      — unassigned events (or use unassigned=true)
  GET /v1/events                   — unchanged, all events

Explicitly NOT in 3B1:
  ❌ GET /v1/tasks/:taskId/runs    — deferred until run_id designed
  ❌ GET /v1/runs/:runId/events    — deferred until run_id designed
  ❌ POST /v1/tasks                — no task CRUD
  ❌ PUT /v1/tasks/:taskId         — no task CRUD
  ❌ DELETE /v1/tasks/:taskId      — no task CRUD
```

Rationale:
1. Smallest new API surface
2. Consistent with event-index query model (`WHERE task_id = ?`)
3. Does not imply a full Task resource API

### 3.7 Security / Trust Boundary (PM Revision 7)

```text
MWT-3B1 is correlation-only, NOT authorization.

X-TrustOS-Task-Id header:
  - Accepted ONLY from trusted local Manager/Gateway context
  - MUST NOT be treated as proof of user permission
  - MUST NOT be used for policy enforcement
  - MUST NOT authorize access to events (query access is separate concern)

Production auth/RBAC: MWT-7 scope. Not in 3B1.
```

Gateway trusts the caller to provide task_id. Gateway does not validate task_id ownership against any identity system. This is acceptable because 3B1 is internal correlation, not multi-tenant authorization.

## 4. Proposed Implementation

### 4.1 event-envelope.ts

Add `task_id` as a mandatory-but-nullable field to the event envelope type:

```typescript
// Additive only — does not change existing fields
// Wire format: snake_case task_id
interface EventEnvelope {
  // ... existing fields unchanged ...
  task_id: string | null;  // NEW: Manager-assigned task correlation ID
                            // Always present on post-3B1 events (string or null)
                            // Historical events may lack this field
}
```

**Key constraints**:
- `task_id` is NOT included in `event_hash` computation. It is metadata, not event content. Changing task association must not invalidate event hashes.
- Wire serialization MUST use `task_id` (snake_case), never `taskId`.
- On post-3B1 events, `task_id` MUST always be present (`string | null`, never omitted, never `""`).
- Historical events without `task_id` are coalesced to `null` at the query/deserialization boundary.

### 4.2 event-index.ts

Add nullable `task_id` column and query support:

```text
Schema addition: ALTER TABLE events ADD COLUMN task_id TEXT;
Index: CREATE INDEX idx_events_task_id ON events(task_id);
Query support:
  - getEventsByTaskId(taskId: string)   — WHERE task_id = ?
  - getUnassignedEvents()               — WHERE task_id IS NULL
  - getEvents(filter?: { taskId?: string | null }) — polymorphic query
```

### 4.3 llm-gateway-server.ts

Gateway accepts `task_id` from the trusted `X-TrustOS-Task-Id` header only:

```text
Input:  X-TrustOS-Task-Id header (string or absent)
Output: task_id: string | null in event envelope

Processing:
  - If header present and non-empty → task_id = header value
  - If header absent or empty → task_id = null
  - Gateway MUST NOT generate, infer, or default task_id
  - Gateway MUST NOT parse task_id from request body, query params, or model output

Wire format: event envelope always uses snake_case task_id
```

### 4.4 Manager/External Caller Propagation

```text
Manager creates Task → gets task_id → propagates to Gateway via header or body metadata
External caller (non-Manager) → may pass task_id if it has one, or omit (null)
```

### 4.5 Migration / Rollback / Rebuild Strategy (PM Revision 5)

```text
Migration (forward):
  ALTER TABLE events ADD COLUMN task_id TEXT;
  CREATE INDEX IF NOT EXISTS idx_events_task_id ON events(task_id);
  Existing rows default to NULL (SQLite behavior for ADD COLUMN).
  One-time, idempotent (IF NOT EXISTS guards).

Rollback tolerance:
  Code MUST tolerate absence of task_id column:
    - If column missing → all task_id queries return empty/null-equivalent
    - No crash, no unhandled error
    - Graceful degradation: task_id filter silently returns no results
  Optionally: migration is one-way with documented restore path:
    - Restore from pre-migration DB backup
    - Or: ALTER TABLE events DROP COLUMN task_id (rebuild index from JSONL)

Rebuild (event index from raw JSONL):
  Rebuilding event index from JSONL MUST populate task_id ONLY if raw event has task_id.
  NO synthetic historical task binding in 3B1.
  Historical events without task_id → NULL in rebuilt index.

Backfill (future, NOT in 3B1):
  Separate PM approval gate required.
  Would involve: mapping known sessions → tasks from task_archives.
  DO NOT implement in 3B1.
```

### 4.6 Query Semantics (PM Revision 6)

```text
GET /v1/events?task_id=<id>:
  Returns events whose indexed task_id exactly equals <id>.
  Case-sensitive exact match.
  Empty array if no events match.

GET /v1/events?task_id=null (or unassigned=true):
  Returns events WHERE task_id IS NULL.
  Includes: post-3B1 events with explicit null + historical events without task_id.
  Historical events without task_id field are coalesced to NULL at query boundary.

GET /v1/events (no task_id filter):
  Existing behavior unchanged.
  Returns all events.
  No implicit task_id filtering.

Query safety:
  task_id filter is AND-composable with existing filters (session_id, event_type, etc.).
  Invalid task_id values (empty string) → treat as no filter (or 400 Bad Request).
```
