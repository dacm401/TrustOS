# ADR-001：数据护栏重述 —— 本地优先存储 + 外发强制加工

> **状态**：ACCEPTED（Boss 决策，2026-08-29）
> **决策者**：Boss
> **影响范围**：修改 TRST-0.3 战略基线中的「raw content 不落库」护栏
> **关联**：`docs/strategy/TRST-0-trustos-architecture-thesis.md`、
> `docs/strategy/trst-system-review-and-competitive-analysis-2026-08-28.md`

---

## 1. 背景

TRST-0.3 冻结的数据护栏为「raw content 不落库」（只存哈希，不存原文）。该护栏
制定于**多用户 / 云端部署**的假设之下，其真实目的是防止数据流向不该去的地方。

随着产品定位明确为 **个人 PC 操作系统（本地 OS，单用户）**，该护栏的适用前提发生变化：

- 多租户隔离风险 → **消失**（本机单用户）
- 云端泄露风险 → **仍存在**（prompt 必须发给云端 LLM）
- 本机存储风险 → **性质改变**：从"泄露给他人"降级为"本机被入侵 / 误传"

同时，Memory 作为用户粘性钩子，需要足够的原始信息才能提供「以便后续查询」的价值，
而纯哈希存储使其几乎无法积累实质内容。

**结论**：原护栏把「本机存储」与「外发传输」混为一谈，在单用户定位下过度限制了本机能力，
却未更精确地覆盖真正的外发风险。

---

## 2. 决策

护栏重述为两条**方向相反**的原则：

| 方向 | 原则 | 说明 |
|---|---|---|
| **入（存储）** | **本地优先，原文存本机** | 原始 prompt / 对话原文存本地，作为 Memory 与回溯的数据源 |
| **出（传输）** | **外发必加工** | 任何发往云端 LLM 的内容必须经过加工管道 |

### 2.1 新护栏表述

> **旧**：raw content 不落库（只存哈希）
>
> **新**：
> 1. **原始数据存本机**（local-first）—— 这是能力，不是风险
> 2. **发往云端的内容必须加工**（egress processing）—— 这是护栏
> 3. **证据链 / 审计导出仍只含哈希** —— 导出物面向第三方，不得含原文

### 2.2 三个暴露面的差异化处置

| 暴露面 | 处置 | 理由 |
|---|---|---|
| ① 本机存储 | ✅ **允许原文**（建议 at-rest 加密） | 单用户，且是 Memory 价值的基础 |
| ② 外发云端 LLM | ⚠️ **必须加工**（最小化 / 脱敏 / 摘要） | 数据离开本机，风险真实存在 |
| ③ 证据链 / 审计导出 | ❌ **仍仅哈希** | 面向第三方验证，不得含原文 |

### 2.3 关键约束：防止「本地存储 → 云端泄露」通道

开放本机存储后，最大新增风险是**检索注入**：

```
raw 存本机 → Memory 检索命中 → 自动注入 prompt → 发给云端 LLM
```

因此强制约束：

- 检索返回的**默认形态为蒸馏物 / 摘要**，而非原文
- 原文默认**不进入外发上下文**
- 原文仅在**本地 UI**按需展示；确需引用进 prompt 时，须用户显式确认

## 3. 未变更的护栏（继续有效）

以下内容**不受本次变更影响**，继续严格遵守：

| 护栏 | 状态 |
|---|---|
| 无语义 DLP 检测（TRST-0.3） | ✅ 保留 —— 敏感识别仍用**模式匹配**，不引入语义模型 |
| Context Boundary：raw history 不发 Worker | ✅ 保留 |
| artifact 原文不发 Manager | ✅ 保留 |
| 证据链不存原文 | ✅ 保留 |
| tamper-evident 而非 tamper-proof | ✅ 保留 |
| 本机单用户，不做 RBAC / 多租户 | ✅ 保留 |

---

## 4. 理由

1. **定位决定威胁模型**：个人 PC OS 的核心资产是本机数据能力；把原文挡在本机之外，
   等于为多租户时代的假设牺牲单用户时代的核心价值。
2. **护栏应守边界而非守介质**：真正的风险是**跨越边界**（本机 → 云端 / 本机 → 第三方），
   而非**存放在本机**。
3. **外发加工比一刀切更精确**：加工管道可按内容敏感度分级处理，
   比"一律不存"在安全性与可用性上都更优。
4. **Memory 价值得以释放**：原文在本机可用后，蒸馏、检索、回溯才有数据源。

---

## 5. 实施要求

| # | 要求 | 关键设计 |
|---|---|---|
| 1 | **外发加工管道** | 挂载于所有 LLM 外发的唯一必经点（`callModelFull` / `callModelStream`），默认开启 |
| 2 | **分层加工** | L0 最小化 → L1 模式脱敏 → L2 摘要化，按需要逐级增强 |
| 3 | **敏感识别用模式匹配** | 复用 `field-classification`，不引入语义 DLP |
| 4 | **加工可观测** | 记录加工**统计**（命中数/类型/削减量），**不记录原文** |
| 5 | **本机存储 at-rest 加密** | 防止物理接触 / 磁盘拷贝场景 |
| 6 | **检索默认返回蒸馏物** | 切断"本地存储 → 云端外发"的自动通道 |

---

## 6. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 本机被入侵 → 原文全泄露 | at-rest 加密；敏感内容（密钥等）仍不存储 |
| 检索注入导致原文外发 | 检索默认返回蒸馏物；原文进 prompt 需显式确认 |
| 加工削弱模型效果 | 加工分级可配置；记录加工统计以便评估影响 |
| 未来转多用户时的技术债 | 存储层按 user 分区设计，保留升级路径 |
