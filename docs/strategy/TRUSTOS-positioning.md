# TrustOS 重新定位 — 从「可信审计」到「连续性基底」

> 状态：战略叙事 v1（基于 2026-10-14 一轮 brainstorm 收敛）
> 决策：保留自有 agent 核心；Hermes 作可插拔 worker 接入主干（借脑不借壳）；审计/证明层正式认栽冻结。

---

## 0. 一句话定位

**TrustOS 是一个让 AI agent「记得住、接得上」的连续性基底：任何引擎（含 Hermes）在其上运行，每一次动作都被原生记录，人随时能重新 orientation——而不是又一个会忘的聊天框。**

---

## 1. 我们放弃了什么（以及为什么）

原 thesis：local-first AI OS + trust control plane（可验证审计 / 对第三方问责）。

判断：**可验证审计是伪需求。**

- 95% 的用户不会去校验哈希、不会去验证 output_hash。
- 这套密码学问责是为「多云 / 不可信模型 / 多租户」威胁模型造的；而产品实际是**单用户本机**，用户本来就信任这个运行时，威胁模型不成立。
- 结论：审计/证明层（evidence / provenance / signed-approval / trust-ref 及其迁移与测试）**正式认栽、标记 deprecated、停止投资**。

> 注：隐私脱敏（DLP / sanitizer）**不是**伪需求——用户确实怕把密钥/隐私泄给云模型。它从「审计」重归类为「隐私」，保留。

---

## 2. 真正的需求是什么（用户自己暴露的）

用户痛点：**多轮真实工作里，自己都记不住之前定了什么、做了什么，导致错误指挥、思路断线。**

这不是「agent 不够聪明」，是**交互媒介的错配**：

- 主流 agent（含终端运行的 Hermes）优化的是「每次 prompt 给个好答案」。
- 但真实工作是在很多轮里推进的，而那个扁平聊天框 / 终端会让人和 agent **一起失忆**。
- 用户要的不是「更聪明的脑」，是「记得我们走到哪、定过什么、哪些线头还悬着」的**连续性**。

---

## 3. 为什么「更好的 UX」是正确战场——但必须说清是哪一层

- **表层 UX（更漂亮 / 更顺）**：桌面上该有的东西，不是差异化；小团队拼不过大厂设计资源。若「更好 UX」指这个，救不了「太相似」。
- **结构性 UX（交互模型）**：agent 与人协作的方式本身不同——从「会忘的聊天」变成「可续接、可重定位的工作空间」。**这才是楔子，且可防守**（见 §4）。

---

## 4. 护城河在哪（关键：避开「浅壳」陷阱）

**反例（浅，必须避开）：** 桌面 UI + Hermes 当黑盒大脑接在后面。
→ 连续性只能是我们并行维护的一本剪贴簿，agent 本身不认它。Hermes 明天就能自己加 UI，我们也随时可被替代。**零护城河。**

**正解（深，选定 A）：** 保留 TrustOS 自有 agent 核心。
- `trst1/llm-gateway-server.ts` 是**所有 model/tool 调用的必经网关**，事件在请求路径里被 `appendEvent` 记录。
- 连续性是 agent **自己的运行轨迹**，原生记录，不是 UI 装饰。
- Hermes 可以进来，但作为我们 Manager 下的 **worker**——它的每个动作也流经主干被记录，**不是 UI 后的黑盒**。

**一句话关系反转：** 我们不是 Hermes 的 UI，我们是 Hermes（及任何引擎）跑在其上的**连续性基底**。定位一反，就从「浅壳」变成「深地基」。

---

## 5. 保留 / 改造 / 认栽 清单

| 类别 | 内容 | 处置 |
|---|---|---|
| 保留并改造 | Event Backbone → 连续性引擎（叙事从「可验证」改为「权威外部记录」） | 核心资产 |
| 保留并改造 | Memory + Postgres（决策/事实持久层） | recap 地基 |
| 保留 | Provider 可插拔（TRST-6） | 借 frontier 脑子补「模型弱」 |
| 保留 | Frontend（Next.js 壳 + dashboard） | 连续性/recap 视图主战场 |
| 保留（降级） | Shadow 默认 | 安静的后端安全姿态，不营销 |
| 保留（重归类） | DLP / 隐私脱敏 | 归「隐私」非「审计」 |
| **认栽冻结** | evidence / provenance / signed-approval / trust-ref 及迁移+测试 | deprecated，停投 |

---

## 6. 赌注与风险（诚实）

- **赌：** 架构原生的连续性 > 调得更好但失忆的循环。
- **风险 1（借脑变借壳）：** 我们核心 raw experience（模型/循环）偏弱，借 Hermes / frontier 是补，但绝不能退化为「黑盒借壳」——Hermes 必须在主干内当 worker。
- **风险 2（剥离成本）：** 代码库大（130+ service 文件），`trust` 命名可能渗入 `app.ts`/`index.ts` 的 wiring；但因 schema ADDITIVE ONLY、envelope 通用，爆炸半径可控，是清理成本非重写成本。

---

## 7. 下一步（接 A 的执行计划，待写）

1. 冻结审计层（标记 deprecated，停投）。
2. 主干原生连续性：Event Backbone 去「证明」叙事，保留 hash/prev_hash（近乎零成本完整性）。
3. Hermes-as-worker 接入点：定义 worker 接口，使其动作流经网关/主干。
4. recap / 续接 UX 层：跨 session、权威、人话的「我们定了什么 / 悬空线头 / 当前状态」。
5. Provider 接 frontier（BYO key）破「模型弱」卡点。
6. 前端改为主战场：连续性视图长在现有 Next 壳上。
