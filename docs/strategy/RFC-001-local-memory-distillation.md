# RFC-001：主权数据战略 —— 本地优先存储 + Memory 增量蒸馏 + 本地模型演进

> **状态**：DRAFT — 待 Boss 拍板后实施
> **日期**：2026-08-29（v2：纳入「主权数据」长期演进路线）
> **前置**：`ADR-001-local-first-egress-processing.md`（已 ACCEPTED，完成「出」侧）
> **决策者**：Boss

---

## 0. 愿景

> **让 Manager 越来越懂你，但数据始终在你机器上——
> 可打包、可加密、可迁移，最终由本地模型读取，而不必交给云端。**

一句话概括当前阶段：

**原文存本机（冷、大、加密），Memory 存蒸馏物（热、小、可注入）；
每轮只对增量做一次蒸馏；检索默认返回蒸馏物而非原文。**

---

## 1. 为什么做

### 1.1 首要动机：保留数据主权（架构动机）

这是本 RFC 的**根本理由**，其余动机均居其次。

**风险的不对称性**（此前被算错了）：

| | 云端（大模型 App） | 本地（TrustOS） |
|---|---|---|
| 泄露状态 | **确定性**——已经发生，每次输入都在别人服务器 | 可能性——需攻击者先入侵 |
| 控制权 | **零**——无法真正删除，可能被训练/审查/封号 | **完全**——可查、可删、可导出、可迁移 |
| 访问者 | 提供商、政府传唤、模型训练 | 只有你 |
| 数据用途 | 训练别人的模型 | 只服务你 |

大众使用大模型 App，是因为**便利**（历史可查、上下文连续）。这个便利是真的。
TrustOS 的差异**不是"更安全"**，而是：

> **同样的可查询、同样的连续性，但数据在你手上。**

| | 大模型 App | TrustOS |
|---|---|---|
| 历史可查询 | ✅ | ✅（本地） |
| 上下文连续 | ✅ | ✅（Memory 蒸馏） |
| 数据可导出 | ❌ 或受限 | ✅ 完全 |
| 真正删除 | ❌ 不可验证 | ✅ 物理删除 |
| 被封号/破产 | 数据随之消失 | 与你无关 |
| 被用于训练 | ✅ 默认 | ❌ 不外发原文 |

**关键认知**：加工解决「**少泄露**」，本地留存解决「**谁拥有**」。
只做加工而不留存，等于**唯一拥有你数据的，是你无法控制的一方**——
此时谈自主权是空话。

### 1.2 次要动机：Memory 是用户粘性钩子（商业动机）

Boss 于 2026-08-24 明确。粘性的本质是**迁移成本**：
系统积累的关于"我"的知识越多，用户越难换。

⚠️ 注意：粘性是**结果**，主权是**理由**。若只有粘性而无主权，
与用大模型 App 并无本质区别——只是换了个地方被锁定。

### 1.3 现状：Memory 几乎是空的

唯一自动写入路径 `autoLearnFromDecision`（`memory-store.ts:146`）有三个硬限制：

| 限制 | 代码证据 | 后果 |
|---|---|---|
| 必须正面反馈才学 | `POSITIVE_SIGNALS`（:144），无反馈则 return（:155） | 绝大多数对话什么都不留 |
| 只记意图分类，不记内容 | `INTENT_RULES`（:134-142）仅产出 `"用户请求过代码类任务（X），使用 Y 效果良好"` | 用户说了什么、决定了什么，全丢 |
| 粒度极粗 | `importance` 固定 2（:177） | 无法区分重要与琐碎 |

用户用了三个月，Memory 里只有几条「做过什么类型的任务」——**主权数据层实际上是空的**。

### 1.4 ADR-001 已把路让开

旧护栏「raw content 不落库」是主要障碍，ADR-001 已重述为
「本地优先存原文 + 外发强制加工」，本机存储不再是禁区。

## 2. 分层主权模型

数据按**主权归属**分四层。云端永远只有 L2，L1 永远在你手上。

| 层 | 内容 | 位置 | 谁控制 | 外发? |
|---|---|---|---|---|
| **L1 原始意图** | 完整 prompt、上下文、对话原文 | **本地**（加密） | 你 | ❌ 从不 |
| **L2 加工产物** | 脱敏/摘要后的 brief | 外发 → 云端留副本 | 你的加工规则 | ✅ 唯一外发层 |
| **L3 模型输出** | 返回结果 | 回落到本地 | 你 | — |
| **L4 云端副本** | L2 的副本 | 云端（不可控） | 提供商 | — |

**关键性质**：
- L1 是**主权层**——永不离开本机，是"越来越懂你"的唯一数据源
- L2 是**交换层**——为换取模型能力而必须让渡的最小代价，且经过加工
- L4 是**已知损失**——不可消除，但因其只含 L2，损失被限定在加工后的信息量

> 若本地不存 L1，则架构只剩"加工"这一半：泄露减少了，但**没有任何东西被保留下来**——
> 唯一拥有完整数据的仍是云端。这正是必须做「入」侧的原因。

## 3. 演进路线（Phase 1 → 4）

> **原则**：每个 Phase 独立可交付、独立有价值。不预设后续 Phase 一定会做，
> 但**架构必须为后续留出空间**（尤其是数据格式与打包结构）。

### Phase 1 — 主权数据层（当前要做的）

**目标**：数据开始在本机积累，Manager 有东西可学。

- 原始对话落本地（加密）
- Memory 增量蒸馏（L0 规则，零成本）
- 检索默认返回蒸馏物

**产出**：可用的本地记忆库。**Phase 2-4 均依赖此层。**

### Phase 2 — 主权数据包（Sovereignty Bundle）

**目标**：数据可打包、可迁移、可长期保存——**主权的物理形态**。

- 周期性打包（按时间/按量，用户可配）
- 强加密（用户口令派生密钥，与登录口令分离）
- 标准格式（自描述，含 schema 版本，向后兼容）
- 可导出/可导入/可校验完整性

**为什么重要**：加密解决了"静态保护"，打包解决了"可迁移"。
**能带走的数据才是你的数据**——否则只是被锁定在这台机器上。

### Phase 3 — 本地模型读取（减少对云端的依赖）

**目标**：用本地模型读懂自己的主权数据，减少把 L2 交给云端的必要。

**关键建议：先 RAG，后微调。**

| 路线 | 做法 | 成本 | 适用 |
|---|---|---|---|
| **RAG（先做）** | 本地嵌入模型 + 向量检索本地数据 | 低（CPU 可跑） | 立即可用；数据可更新 |
| **微调（后做）** | LoRA 微调小模型（1.5B~3B）内化偏好 | 中（需 GPU、需数据积累） | 数据足够多之后 |

**为什么先 RAG**：
- 无需训练，数据立即可检索
- 新数据即时生效（微调是静态快照，需重新训练）
- 数据稀疏期（刚积累）微调无意义

**诚实预期**：本地模型能力远弱于云端大模型，**不能替代复杂推理**。
但用于「理解用户偏好 / 记忆检索 / 个性化」这类任务，小模型足够——
这恰恰是主权数据的主要用途。

### Phase 4 — 自主闭环（远期，仅预留）

**目标**：本地数据 + 本地模型形成闭环，云端退化为可选增强。

- 简单任务完全本地完成
- 仅复杂推理调用云端，且仍走 L2 加工
- 用户可配置"云端依赖度"

**不做承诺**：此阶段的可行性取决于本地模型能力的演进，
本 RFC 仅在**数据格式与接口**上预留空间，不做技术承诺。

## 4. 主要策略（核心）

### 策略一：双存储分离（Two-Store）

| | **Raw Store（原文）** | **Memory Store（蒸馏物）** |
|---|---|---|
| 内容 | 完整对话原文 | 结构化条目（事实/偏好/决策/约束） |
| 体积 | 大 | 小 |
| 温度 | 冷（按需读取） | 热（可注入 prompt） |
| 加密 | ✅ at-rest | 否（本就不含敏感原文） |
| 可否进 prompt | ❌ **默认不可** | ✅ 可 |
| 关系 | 被指针引用 | 持有 `source_ref` 指回原文 |

**为什么必须分离**：如果两者合一，检索时就会把原文捞出来注入 prompt，
直接打通「本地存储 → 云端外发」的通道（ADR-001 §2.3 明令禁止）。
分离是**结构性**地切断该通道，而不是靠代码自觉。

### 策略二：增量蒸馏（Incremental Distillation）

**关键**：只对**本轮新增**部分蒸馏，不重新处理整个 history。

```
轮次 N：只蒸馏 turn_N 的新增内容  →  O(1)
而非：  蒸馏 history[0..N]        →  O(N)
```

**分层，成本递增**：

| 层 | 手段 | 成本 | 覆盖 |
|---|---|---|---|
| **L0 规则** | 正则/关键词匹配显式信号 | **0** | "以后都…" "记住…" "我喜欢…" "我们决定用 X" "不要…" |
| **L1 模式** | 项目事实、技术栈、命名约定 | 极低（本地） | 从代码/配置中识别 |
| **L2 语义** | 调 fast model 做结构化抽取 | 有（按次计费） | 仅当 L0/L1 无产出且信号强 |

**异步执行**：蒸馏不阻塞响应（沿用 `learnFromInteraction` 的 fire-and-forget），
用户感知不到延迟。

### 策略三：检索默认返回蒸馏物（安全关键）

这是 ADR-001 §2.3 的落地：

- 检索结果**默认是蒸馏物/摘要**，不是原文
- 原文只在**本地 UI**按需展示（满足"以便后续查询"）
- 原文进 prompt **必须用户显式确认**

**额外收益**：这也顺带解决 token 效率——当前每轮固定重发最近 6 轮 raw
（`llm-native-router.ts:1350` `slice(-6)`），改为蒸馏物后外发量显著下降。

### 策略四：可治理优先（Governance First）

**错误的记忆比没有记忆更糟**——它会持续误导后续每一轮。

| 机制 | 说明 |
|---|---|
| **provenance** | 每条自动记忆记录来源对话，可追溯、可一键回溯原文 |
| **置信度分级** | 高置信度自动写入；低置信度进「待确认」队列 |
| **用户控制** | 可删、可改、可降权（Memory Governance 界面已有基础） |
| **冷启动保守** | 初期只开 L0（零成本、零风险），观察准确率后再谈 L1/L2 |

### 策略五：敏感度分级存储

| 内容 | 是否存原文 | 备注 |
|---|---|---|
| 普通对话 | ✅ 存（加密） | |
| 显式记忆（"记住…"） | ✅ 存 | 且写入 Memory Store |
| **密钥/密码/token** | ❌ **永不存** | 复用外发加工的模式库（`egress-processor.ts`） |
| 第三方隐私信息 | ⚠️ 存但标记 `sensitive` | 不自动进 Memory、不自动进 prompt |

## 5. 好处

| # | 好处 | 说明 |
|---|---|---|
| 1 | **数据主权** | 能带走、能删除、不被训练 —— 相对云端 App 的根本差异 |
| 2 | **粘性成立** | Memory 随使用真正积累，迁移成本提高 |
| 3 | **可查询回溯** | 命中 Memory，需要详情回溯原文 |
| 4 | **外发面缩小** | 蒸馏物替代 raw history 重发，发给云端的数据更少（**安全性不降反升**） |
| 5 | **token 成本下降** | 增量蒸馏 + 蒸馏物注入，比固定重发 6 轮原文省 |
| 6 | **演进空间** | 为 Phase 2-4（打包迁移 / 本地模型）留出基础 |
| 7 | **成本可控** | L0 零成本即可覆盖大部分显式指令 |

## 6. 坏处与代价（诚实列出）

| # | 坏处 | 严重度 | 缓解 |
|---|---|---|---|
| 1 | **本地攻击面变大** | 高 | 本机存了更多原文 → 机器被入侵后果更严重。需 at-rest 加密 |
| 2 | **at-rest 加密的固有局限** | **高（必须诚实）** | 密钥若存同机，加密只能防「磁盘被偷/文件被拷」，**防不了「机器被控」**。这是单机场景的固有边界，无法靠应用层解决 |
| 3 | **记忆污染风险** | 高 | 错误记忆持续误导。靠 provenance + 待确认队列 + 用户治理 |
| 4 | **存储持续增长** | 中 | 需保留期策略 + 归档/清理机制 |
| 5 | **复杂度上升** | 中 | 新增 2 张表 + 1 个服务 + UI 改动。分阶段实施控制风险 |
| 6 | **蒸馏质量不确定** | 中 | L0 规则蒸馏召回率低但**精确率高**；先跑 L0 验证价值 |
| 7 | **L2 语义蒸馏成本** | 低 | 完全可选，默认关闭 |

### 4.1 关于加密，必须说清楚

| 方案 | 防什么 | 防不了什么 | 体验代价 |
|---|---|---|---|
| **不加密** | — | 任何本地访问 | 无 |
| **应用层加密（密钥同机）** | 磁盘被偷、文件被拷 | **机器被控**（密钥也在机上） | 无 |
| **用户口令派生** | 上述 + 未登录访问 | 机器被控且内存被读 | **每次启动输密码** |
| **依赖 OS 全盘加密**（BitLocker/FileVault） | 磁盘被偷 | 机器被控 | 无（用户自行开启） |

**我的建议**：推荐 **应用层加密（密钥同机）+ 文档提示用户开启 OS 全盘加密**。
理由：在不牺牲体验的前提下防住最常见的「设备丢失/文件外传」场景；
对「机器被控」这一威胁，**诚实承认应用层无解**，不制造虚假安全感。

## 7. 怎么做（Phase 1 详细设计）

每阶段独立可交付、独立可回滚。

### 阶段 0：Raw Store（原文存储层）

**做什么**
- 新表 `conversation_turns`：`id / session_id / turn_index / role / content /
  created_at / content_hash / sensitivity`
- 落库时机：每轮对话完成后异步写入（不阻塞响应）
- 敏感过滤：复用 `egress-processor.ts` 的模式库，命中密钥类 → **不落库**
- at-rest 加密（按 §4.1 待确认方案）

**DoD**
- 对话原文可持久化、可按 session 读取
- 密钥类内容确认不落库（单测覆盖）
- 写入失败不影响主流程（异步 + 容错）

### 阶段 1：L0 规则蒸馏（零成本，价值立现）

**做什么**
- 新增 `src/services/memory/distiller.ts`
- 规则集（正则/关键词）：
  - 显式指令：`以后都…` / `记住…` / `别忘了…`
  - 偏好：`我喜欢…` / `我偏好…` / `用 X 不要用 Y`
  - 决策：`我们决定…` / `就按 X 来` / `确定用 X`
  - 约束：`不要…` / `别…` / `必须…` / `禁止…`
- 分类写入：`preference` / `fact` / `context` / `instruction`
- 每条带 `source_ref`（指回 `conversation_turns.id`）+ `confidence`
- 高置信度 → 直接写入；低置信度 → 写入但标记 `status: pending`

**为什么先做 L0**：零调用成本、零模型依赖、精确率高（显式信号几乎不会误判）。
**能立即验证「Memory 是否真的有价值」**，再决定是否投入 L1/L2。

**DoD**
- `npm run verify:distill` 规则蒸馏单测全绿
- 实际对话中，说"记住我喜欢用 TypeScript"能在 Memory 中查到
- 无 LLM 调用（成本为 0）

### 阶段 2：检索与注入边界（安全关键）

**做什么**
- `retrieve()` 默认返回**蒸馏物**，不返回原文
- 原文读取走独立 API `GET /v1/conversations/:id/turns`，仅供本地 UI
- Context Package 注入时只用蒸馏物（`sendMemoryToWorker` 已有开关）
- **硬约束**：原文进 prompt 必须显式传 `includeRaw: true` 且记录审计事件

**DoD**
- 检索路径无原文外发（单测 + 代码审查双重确认）
- 原文仅在本地 UI 可见

### 阶段 3：治理 UI

**做什么**
- Memory 列表展示 `source`（来源）+ `confidence` + `provenance` 链接
- 「待确认」队列：用户可批准/拒绝/编辑
- 一键回溯原文（跳转到对应 turn）
- 删除/降权

**DoD**
- 每条自动记忆可追溯到来源对话
- 用户可否决任何自动提取的记忆

### 阶段 4（可选）：L2 语义蒸馏

**做什么**
- 对 L0/L1 无产出的高价值对话，调 fast model 做结构化抽取
- 默认关闭，`TRUSTOS_MEMORY_DISTILL_LEVEL=semantic` 开启

**前置条件**：阶段 1 跑一段时间，确认 L0 的价值与缺口后再决定。

## 8. 风险登记

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 记忆污染（错误记忆误导） | 中 | 高 | provenance + 待确认队列 + 用户治理 + 冷启动只开 L0 |
| 本地攻击面扩大 | 低（本机自用） | 高 | at-rest 加密 + 敏感过滤 + 保留期 |
| 蒸馏规则误提取 | 中 | 中 | 精确率优先（宁可少提，不可错提）；低置信度进待确认 |
| 存储膨胀 | 中 | 低 | 保留期策略 + 归档 |
| 原文意外外发 | 低 | **极高** | 结构性分离（Two-Store）+ 阶段 2 硬约束 + 单测 |
| **加密与检索的矛盾** | **确定存在** | 中 | 见下方专项分析 |
| 本地模型能力不足（Phase 3） | 高 | 中 | 明确定位为"个性化/检索"，不替代复杂推理 |
| 硬件门槛（Phase 3） | 中 | 中 | RAG 可 CPU 跑；微调需 GPU，按用户硬件可选 |

### 8.1 专项：加密与可检索性的矛盾（Phase 3 绕不开）

**问题**：`at-rest 加密` ≠ `加密状态下可检索`。
若主权数据强加密存储，本地模型要读取它，必须先解密——
那么"加密"保护的是**静态数据**，而非**使用中的数据**。

| 方案 | 检索 | 保护范围 | 现实性 |
|---|---|---|---|
| 全量明文 | ✅ 直接 | 无 | 最简单，但无保护 |
| 全量加密 + 用时解密 | ✅ 需先解密 | 静态数据（设备丢失） | **现实方案** |
| 同态加密 | ✅ 密文检索 | 全程 | **不现实**（性能差 3~5 个数量级） |
| **分层**：索引明文 + 内容加密 | ✅ 走索引 | 内容本体 | **推荐**（元数据泄露可控） |

**建议**：采用**分层方案**——
- **索引/元数据**（时间、类型、标签、摘要）明文，供检索与 UI 展示
- **原文与蒸馏物内容**加密，读取时解密到内存

理由：元数据泄露的损害远小于内容泄露，而检索效率得以保留。
这与「外发加工」的哲学一致：**按敏感度分级，而非一刀切**。

⚠️ 此矛盾**无法被消除**，只能被管理。Phase 3 设计时必须明确接受这一点。

## 9. 验证方式

- 每个阶段新增对应验证脚本，纳入 `npm run verify:trust`
- 阶段 2 后增加**外发内容审计**：断言实际发出的 messages 中不含原文片段
- 全程保持「外发加工」已建立的护栏不回退
